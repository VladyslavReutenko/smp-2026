## 1. Яку задачу розв'язує SQL і хто кінцевий користувач

SQL (Structured Query Language, "структурована мова запитів") — це предметна мова для роботи з реляційними базами даних: збереження, пошуку, зміни й видалення структурованої інформації, організованої у вигляді таблиць.

Задача, яку розв'язує SQL, виникає там, де даних багато, вони повʼязані між собою, і до них треба звертатись швидко й точно. Уявімо чат-бота з тисячами користувачів і мільйонами повідомлень. Зберігати все це в одному текстовому файлі чи в оперативній памʼяті неможливо — файл стане величезним, пошук повільним, а дані можуть загубитись при збої програми. База даних і SQL вирішують саме цю проблему: дані зберігаються окремо від програми, надійно, і до них можна звертатись запитами, не переписуючи увесь файл.

Кінцевий користувач SQL — не той, хто просто листується з чат-ботом, а **розробник** або **адміністратор системи**: людина, яка створює структуру бази (таблиці користувачів, повідомлень, налаштувань) і пише запити, щоб отримати потрібну інформацію — наприклад, "скільки користувачів приєдналось за останній тиждень" чи "яке було останнє повідомлення від конкретного користувача".

## 2. Мінімальний робочий приклад коду з поясненням

Розглянемо спрощену базу даних чат-бота з двома таблицями: `users` (користувачі) і `messages` (повідомлення).

**Створення таблиць:**

```sql
CREATE TABLE users (
    id INTEGER PRIMARY KEY,
    username TEXT NOT NULL,
    joined_at DATE
);

CREATE TABLE messages (
    id INTEGER PRIMARY KEY,
    user_id INTEGER,
    text TEXT,
    sent_at DATETIME,
    FOREIGN KEY (user_id) REFERENCES users(id)
);
```

Пояснення: `CREATE TABLE` створює нову таблицю з переліком колонок і їхніх типів. `PRIMARY KEY` — унікальний ідентифікатор рядка (щоб відрізняти одного користувача від іншого). `FOREIGN KEY` у таблиці `messages` — це посилання на конкретного користувача з таблиці `users`: так SQL "знає", яке повідомлення кому належить, не дублюючи всю інформацію про користувача в кожному повідомленні.

**Додавання даних:**

```sql
INSERT INTO users (id, username, joined_at)
VALUES (1, 'vlad', '2026-09-20');

INSERT INTO messages (user_id, text, sent_at)
VALUES (1, 'Привіт, боте!', '2026-09-28 14:30:00');
```

**Запит — отримати всі повідомлення конкретного користувача:**

```sql
SELECT messages.text, messages.sent_at
FROM messages
JOIN users ON messages.user_id = users.id
WHERE users.username = 'vlad';
```

Пояснення: `SELECT` каже, які колонки показати (тут — текст повідомлення й час). `FROM messages` — з якої таблиці брати основні дані. `JOIN users ON ...` — обʼєднує таблицю повідомлень із таблицею користувачів за збігом `user_id = id`, щоб можна було фільтрувати за іменем користувача, а не за внутрішнім числовим ідентифікатором. `WHERE` — умова фільтрації: лишити тільки рядки, де ім'я користувача дорівнює `'vlad'`.

Цей запит — мінімальний, але робочий приклад того, як SQL дозволяє "з'єднувати" дані з різних таблиць в один осмислений результат, не переписуючи й не дублюючи інформацію.

## 3. Вдале й невдале рішення в синтаксисі SQL

**Невдале рішення — вразливість SQL-injection.**

Якщо розробник формує запит простим склеюванням рядків, підставляючи туди текст прямо від користувача:

```python
# НЕБЕЗПЕЧНО — так робити не можна
username = input()  # користувач вводить своє імʼя
query = "SELECT * FROM users WHERE username = '" + username + "'"
```

Якщо користувач введе не звичайне ім'я, а спеціально підготовлений рядок на кшталт: ' OR '1'='1
то фінальний запит перетвориться на:
```sql
SELECT * FROM users WHERE username = '' OR '1'='1'
```
Умова `'1'='1'` завжди істинна, тому такий запит поверне **всіх** користувачів бази, а не одного конкретного — зловмисник обходить перевірку і отримує доступ до чужих даних. Це класична атака, відома як **SQL-injection**, і вона реально траплялась у великих системах через саме таку необережність.

**Вдале рішення — параметризовані запити.**

Правильний підхід — не склеювати текст запиту руками, а передавати введені дані окремо, через спеціальні "плейсхолдери":

```python
# БЕЗПЕЧНО
username = input()
cursor.execute("SELECT * FROM users WHERE username = ?", (username,))
```

Тут символ `?` — це місце, куди база даних сама підставить значення `username`, **розуміючи**, що це саме дані, а не частина коду запиту. Навіть якщо користувач введе `' OR '1'='1`, це значення буде сприйняте буквально як текст імені, а не як частина SQL-синтаксису — атака не спрацює.

Різниця між цими двома підходами показує важливий принцип роботи з предметними мовами: синтаксис, який виглядає схоже, може мати кардинально різні наслідки залежно від того, як саме дані потрапляють у запит.

## 4. Чим це робилося б без SQL і чому було б гірше

Без SQL дані довелося б зберігати в звичайних файлах — наприклад, у текстовому форматі (CSV) чи взагалі в оперативній памʼяті програми, без збереження на диск. Для невеликого чат-бота з кількома користувачами це могло б спрацювати, але з'являються серйозні проблеми:

**Швидкість пошуку.** Щоб знайти всі повідомлення одного користувача серед мільйона рядків у текстовому файлі, довелось би послідовно перечитувати весь файл щоразу. Бази даних з SQL використовують **індекси** — спеціальні структури, які дозволяють знаходити потрібні рядки миттєво, без перегляду всього масиву даних.

**Цілісність даних.** У звичайному файлі ніщо не заважає записати повідомлення від користувача, якого не існує (помилка в `user_id`). SQL із `FOREIGN KEY` сам стежить за тим, щоб такі зв'язки були коректними, і не дозволить створити "повідомлення в нікуди".

**Одночасний доступ.** Якщо кілька процесів одночасно читають і пишуть у звичайний файл, легко отримати пошкоджені дані (один процес записує, поки інший читає той самий рядок). Бази даних, керовані через SQL, мають вбудовані механізми, що гарантують коректність навіть при одночасних запитах від багатьох користувачів.

Отже, без SQL довелось би самостійно "винаходити" всі ці механізми — індексацію, перевірку зв'язків, безпечний одночасний доступ — що означає значно більше коду, більше місць для помилок і значно повільнішу роботу зі зростанням обсягу даних.

## Висновок

SQL розв'язує конкретну й поширену задачу — надійне, швидке й структуроване зберігання повʼязаних даних. Його синтаксис дозволяє виразити складні запити ("знайти всі повідомлення конкретного користувача за останній тиждень") кількома рядками, замість десятків рядків коду на мові загального призначення. Водночас, як показує приклад SQL-injection, той самий синтаксис вимагає обережності: невдале використання може призвести до серйозної вразливості, тоді як коректний підхід (параметризовані запити) повністю її усуває.
